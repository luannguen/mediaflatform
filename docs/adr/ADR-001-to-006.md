# 📜 ARCHITECTURE DECISION RECORDS (ADR-001 to ADR-006)

---

## ADR-001: Media as an Independent Service
- **Status**: Accepted
- **Context**: Multiple apps (Commerce, Community, CMS) need media storage. If each manages its own storage, fragmentation, duplicates, and vendor lock-in occur.
- **Decision**: Media Platform is built as a standalone headless service with REST API v1.
- **Consequence**: All client apps delegate media management via API; no direct database sharing.

---

## ADR-002: Asset IDs Instead of Storage URLs as Domain Identity
- **Status**: Accepted
- **Context**: Storage bucket URLs (CDN domains, S3 keys) change during migrations or reconfigurations.
- **Decision**: External apps must store `media_id` (`med_...`) instead of fixed image URLs. URLs are resolved dynamically by Media Platform.
- **Consequence**: Storage providers can be migrated with zero broken image links in products or articles.

---

## ADR-003: Multi-Tenant Workspace Boundary
- **Status**: Accepted
- **Context**: Enterprise needs separation between Production, Marketing, and Staging assets.
- **Decision**: `Workspace` is the mandatory isolation boundary. All queries enforce `workspace_id` server-side.
- **Consequence**: Guaranteed tenant privacy; cross-workspace leaks are impossible.

---

## ADR-004: API Key Salted Hashing
- **Status**: Accepted
- **Context**: Exposing plaintext API keys in databases creates a severe compromise risk.
- **Decision**: Raw keys (`mda_live_...`) are shown once to the developer. Database stores only `key_prefix` and HMAC-SHA256 hash.
- **Consequence**: Even full database dumps cannot extract usable API tokens.

---

## ADR-005: Storage Provider Abstraction Layer
- **Status**: Accepted
- **Context**: Current deployment uses Supabase Storage, but future cost optimization may require Cloudflare R2 or AWS S3.
- **Decision**: Domain code interacts exclusively through `StorageProvider` interface.
- **Consequence**: Switching cloud providers requires only swapping the adapter class.

---

## ADR-006: Asset Reference Tracking & Safe Delete Protection
- **Status**: Accepted
- **Context**: Accidental asset deletion by administrators causes broken images on live production stores and portals.
- **Decision**: External apps register usage via `asset_references`. Permanent delete is blocked with `ASSET_IN_USE` if active references exist.
- **Consequence**: 100% elimination of 404 broken image incidents.
